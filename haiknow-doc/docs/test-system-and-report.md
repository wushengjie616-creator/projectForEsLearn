## 风险与缺口

### R1：双用户交叉隔离尚未验收（发布阻断）

当前 `.local/invite-codes.json` 只有一个真实邀请码。代码中的查询普遍显式限定 `user_id`，数据库外键也绑定 `(id, user_id)`，这是正向静态证据；但没有第二个身份就无法证伪“用户 A 能读取、修改或删除用户 B 数据”的真实故障。

复测至少应覆盖：

1. A 创建材料、练习、答题记录和阅读进度；
2. B 用 A 的材料 ID、练习 ID、阅读 slug 调用所有读取、提交和删除入口；
3. 预期为 404/拒绝且 A 数据不变；
4. B 的配额统计不得包含 A 数据；
5. 清理全部探针并分别回读 A、B 原始记录。

### R2：内存限流不构成部署级全局限流（中风险）

四个 AI 路由使用进程内 `Map` 计数。它能限制单进程请求，但在多实例、冷启动或实例回收后会重置；部署到 serverless 环境时不能作为可靠的费用或滥用边界。当前未部署、用户上限不超过 10 人，风险暂可接受，但上线前需要共享持久限流或供应商侧预算上限，并增加跨实例验收。

### R3：10 MiB 配额存在并发竞争窗口（中风险）

当前流程先汇总 `storage_bytes` 再插入，数据库只校验单行 `storage_bytes > 0`，没有对用户总量做原子约束。两个并发请求都可能在检查时看到剩余空间并随后同时插入，导致总量超过软配额。它不会造成跨用户泄漏，但会削弱容量边界。上线前应增加并发压力用例，并决定使用数据库事务/锁、原子 RPC 或容忍小幅软超限。

### R4：API 路由层自动化覆盖不足（中风险）

现有测试对 DeepSeek handler、领域逻辑和组件覆盖较好，但五个 API Route Handler 缺少直接自动化测试。handler 层已覆盖新增文章接口的未认证、输入、限流、结构校验及 402 分类，但路由装配中的 404、429、503、507、超时、答案持久化失败及用户 ID 传递仍未被直接覆盖。应补充路由级测试，且至少对错误分支做轻量 mutation check。

### R5：本轮未执行付费 AI、移动真机与部署验收（范围限制）

既有 `verify:custom-learning-e2e` 已在此前授权下验证材料、练习、批改和清理；新增“AI 写文章 → 用户确认转换”会额外产生一次真实 DeepSeek 调用，本轮未在缺少新一轮付费调用明确授权时执行。Vercel 尚未配置，也没有浏览器自动化或真机设备入口。README 中 2026-08-27 的历史成功记录只能作为原有链路证据，不能替代新增文章流程复测。

## 发布判定

当前版本可进入单用户本地试用，不能仅凭本报告宣称满足完整首阶段验收。解除条件通过至少需要：

1. 完成 R1 双邀请码交叉隔离并保留清理证据；
2. 经授权执行一次包含“AI 写文章 → 转换 → 复看 → 出题 → 批改 → 清理”的付费 AI E2E；
3. 对 R2/R3 给出上线前处置决定；
4. 部署后完成桌面与移动端关键流程验收。
